# Arcanum — Covenant Release Qualification Review, 2026-08-25

**Date:** 2026-08-25 · **Range:** `ac3639dc..6f61485c` (25 commits, 224 files, +12,184 / −1,518) · **Status:** complete, eleven findings open

Scope: the Covenant candidate tree — the durable operator-and-agent profile injected into every turn, with Global and Campaign scopes, an operator-authored Confirmed lane rendered in CONTEXT, an agent-authored Proposed lane rendered as fenced hardened DATA, a Retired tombstone lifecycle, and the whole feature off by default behind `Arcanum:Features:Covenant`. Five domains were reviewed: specification conformance, code quality, security, performance, and repository integration.

This pass differs from [the 2026-08-18 pass](Arcanum.Review.20260818.md) in the standard of evidence it demanded rather than in its breadth. That pass reviewed the whole tree; this one reviews one feature's candidate range, and it does so after two earlier adversarial audits of the same range had each found the identical class of defect: a fix reported as proven, carrying a passing test, that no production caller could reach because an optional parameter defaulting to `null` was never supplied under `src/`. A mutation check did not catch it, because the test invoked the mutated code directly. Every reviewer in this pass was therefore required to name the production call path under `src/`, with `file:line`, for anything they claimed was delivered or broken — a finding that could not be substantiated that way did not count as a finding.

## Method

Five read-only finder agents ran one per domain. Each finding was then handed to an **independent adversarial verifier** whose default verdict is *refuted*, which re-opened every cited file at every cited line, re-derived the line numbers with `grep` rather than trusting the handed citations, and traced the production path itself. Verifiers were told that a report's own confidence is not evidence and that an ambiguous sentence a maintainer would reasonably leave standing is not an actionable finding.

The verification pass mattered. It refuted three findings outright, and two more survived only in reduced or narrowed form — the security finding lost its production-reachability claim entirely, and the integration finding lost the half of its evidence that turned out to have been manufactured by this review workflow rather than by the candidate tree. In two cases the correction went the other way, with the verifier finding the defect to be *worse* or more widely spread than the finder reported.

Because the same optional-parameter defect had twice survived a passing test, the consolidation pass re-verified the reachability of every surviving finding a third time rather than accepting it. The most important of those checks: `WizardIntelligenceProvider`'s constructor takes `CovenantDispatchGate? covenantDispatch = null` at `WizardIntelligenceProvider.cs:97` — exactly the shape that fooled both earlier audits — and it is genuinely supplied in production, because `ApiBootstrapper.cs:447` registers the gate unconditionally and `:455` constructs the provider through `ActivatorUtilities.CreateInstance`, which resolves the registered service rather than falling back to the default. The composed dispatch path is live, so the findings that rest on it describe real production behaviour.

## Specification conformance

Examined: `Arcanum.DESIGN.md` §10.10–§10.24 with §10.21–§10.24 read line by line, `Arcanum.OATH.md` §2.1/§2.2 and the Covenant slice rows, `Arcanum.API.md` §8.22/§8.28/§8.29, `Arcanum.Command.Reference.md` lines 588–616, `Compendium.README.md`, and the Covenant paragraphs of `README.md` — each checked against the registered routes in `CovenantMutationEndpoints.cs` and `CovenantInspectionEndpoints.cs`, the live command tree in `CliCommandTree.Covenant.cs`, and the committed `Arcanum.CommandMap.json`.

**The engineering claims hold; the documentation layer does not.** Every headline "delivered" assertion was chased to a production call path and found real — the dispatch gate, the `covenant:` argument reaching `SystemPromptBuilder`, the turn committer resolved through DI rather than through its optional default, the tool-capability mint, the status census, and the CI benchmark lane. No instance of the two prior audits' defect class survives in this range. What is broken is traceable to one source edit: late in the range the `/query` inspection route was un-mapped, dropping the registered count from ten to nine, and the sentences describing it were updated in some documents and not others.

Two findings survive, and together they are one editorial pass. The first is the `/query` cluster: five present-tense statements across four governed documents still say the free-text route is registered and refuses, when nothing routes to it and `ICovenantManagementService.QueryAsync` retains its refusal only for a stale caller. This is an in-range regression rather than pre-existing drift — `git show ac3639dc:src/RetroDownfall.Arcanum.Api/Tower/CovenantInspectionEndpoints.cs` has six `MapPost` calls including `/memory/covenant/query`, and HEAD has five. The second is the Command Reference's four-row table, which gives every shipped verb a `--global` flag registered on no command, gives `list` a `--query` option it does not have while the prose three lines above says the option does not exist, states that a scope selector is required when omitting `--campaign` resolves to Global, and promises an interactive content prompt that `ReadContentAsync` explicitly refuses. Both findings matter more than documentation findings usually do, because the Command Reference is the operator-facing contract for a surface that became reachable for the first time inside this very range.

Refuted: the claim that `Compendium.README.md:38` makes a stale existence assertion about the management routes and the `arcanum memory covenant` commands. The verifier read the document structure rather than the sentence in isolation and found line 38 to be item seven of a numbered list under the **Public configuration contract** heading, every other clause of which is configuration-scoped. Read in that frame, "not included and will add none" means the routes and verbs add no configuration key, which is true. The finder had already conceded the sentence was ambiguous rather than false; ambiguity a maintainer would reasonably leave is not actionable.

Clean and worth recording: the issue-reference rule holds across all ten governed documents — the only bare hash-and-digits hits outside Markdown anchors are five upstream .NET runtime defect references, all of them present at `ac3639dc` and none of them this repository's tracker. The `MemoryStatusDto.covenant` field list in the API document matches `CovenantStatusDto` member for member. The `ProviderToolCallBuffer` withdrawal is consistently applied in every direction, leaving no stale reference in source, error catalogue, design record, or README. The DCI suite definition in the OATH resolves to exactly the seven trait-carrying classes it describes, with a membership test deliberately sitting outside its own filter.

## Code quality

Examined in full rather than as diff hunks: `CovenantLinker.cs`, `CovenantTurnPlan.cs`, `CovenantSectionCapacity.cs`, `CovenantCompiler.cs`, `CovenantMutationContracts.cs`, the four `Core/Performance` benchmark types, the preview assembly and admission in `WizardIntelligenceProvider.ContextPreview.cs`, the dispatch admission block and `ResolveCovenantAdmission` in `WizardIntelligenceProvider.cs`, `CovenantDispatchGate.cs`, `CovenantContextProvider.cs`, the quota guard, mutation kernel and store, and the new composed provider test file. The blank-line formatter gate was run repo-wide and reports zero files needing change.

**The tree is broadly well-constructed**, and its main structural claim survives scrutiny: `CovenantSectionCapacity` genuinely eliminates the renderer-versus-quota-guard duplication it was created for, with one implementation called from both sides and the one place they could still disagree — fence length across a fragment boundary — closed by a new snapshot invariant requiring every fragment to end with LF and carry no interior LF. Lease disposal is correct on every path traced. The withdrawn streaming tool-call buffer took its orphaned classifier overload with it.

Three important findings survive, and the first two are the same defect class the earlier audits found: a code path whose stated contract is contradicted by its own production caller. `WizardIntelligenceProvider.ContextPreview.cs` builds the preview prompt *with* the plan-rendered Covenant and then hands those same messages to `ResolveCovenantAdmission`, whose own XML remark states that head-room "is measured against the transcript as it stands before any Covenant bytes exist, which is the only measurement that is not circular" — while the dispatch path it was explicitly changed to mirror clears the Covenant first and says so in a comment. The preview is therefore systematically more pessimistic than the turn it claims to report, and because it never rebuilds after admission, it can print "withheld entirely, nothing was sent" beside a non-zero token count for that same section. `CovenantLinker.Link`'s new catch is scoped to `ArgumentException`, so it absorbs every invariant throw in the linker's own call tree — including the lane-versus-placement guard added in this same range, and every `ArgumentNullException.ThrowIfNull` on the path, since that type derives from `ArgumentException` — and relabels them all as stored-Covenant corruption, pointing an operator at data that is fine. The degradation is not fully silent, as the finder claimed: the dispatch gate logs a Warning. But it logs only `Error.Code`, always the same integrity-failure code, and the caught exception is bound in the filter and never used, so type, message and stack are discarded. Third, the one test file that composes the provider with a real dispatch gate — created in this range precisely because "the dispatch block is unreachable under test and deleting it leaves the suite green" — asserts only two negatives, one with no gate at all and one driving a deliberate refusal. Neither can enter the branch that injects admitted content into the prompt, and no other test in the suite inspects what the provider actually dispatched, so the feature's entire happy path is asserted by nothing.

Two minor findings survive. The CI step that uploads the benchmark run carries a comment explaining why it deliberately has no condition, and the explanation is false: the workflow's own job parser skips any line that is not at indent four before it looks for `if:`, a step-level `if:` sits at indent eight, and the coverage upload in another job already carries `if: always()` with the suite green. Without a condition the step defaults to `if: success()`, and the preceding gate step exits non-zero on a ceiling breach — so the run that matters most is the one systematically discarded, even though the host writes the JSON to disk before it evaluates the gate. Separately, a field declaration was inserted between `CovenantDispatchGate`'s `Record` documentation and the method it documents, so the whole block including the rationale for the logging decision binds to the field, the field's generated documentation carries two summaries, and the method carries none.

Refuted: the claim that `BenchmarkHarness`'s discarded `Stopwatch.GetElapsedTime` result is load-bearing and needs a comment defending it. The finder argued that removing it would bias every allocation baseline because the measured loop pays the same cost inside its own window. The verifier checked the premise and it is wrong — the control loop's sample is purely a `GC.GetTotalAllocatedBytes` delta, neither `GetTimestamp` nor `GetElapsedTime` allocates, and the measured loop writes its timings into buffers allocated before the snapshot. The discard has no effect, so there is nothing a maintainer would change.

## Security

Examined: the AES-256-GCM envelope codec and its master key provider in full, the mutation contracts and kernel including the nullable Campaign registry epoch, the lease and operation gate with all eight `ValidateLeaseAsync` call sites, the disclosure-before-egress ordering across both buffered and streaming entry points, the MCP internal tool surface and both Covenant tool handlers, the Proposed-lane fence rendering, the residence latch narrowing, and every interpolated string and SQL statement in the Covenant tree.

**One finding survives, it is minor, and its production-reachability claim was refuted.** Everything else resolved clean, several of them for non-obvious reasons. The envelope codec bounds its caller-asserted issued-at stamp in both directions, and the optional parameter that carries it is genuinely supplied by `CovenantMutationService.PrepareAsync` — checked specifically because that is this tree's known trap. Nonce discipline holds across re-keys, because a fresh random generation salt enters every derived purpose key, so a generation transition that resets counters cannot repeat a key-and-nonce pair. Three refusal shapes exist rather than one, and each is safe for a different reason: the purpose mismatch fires before any cryptography but discloses only a byte the caller can read from the token's own plaintext header, and the expiry and staleness refusals fire only after the tag has verified. Agent-authored writes cannot reach canonical state on any path — `ICovenantMutationCollector.Seal` has no caller anywhere under `src/`, and the only production disposition is `Discard()`. The Proposed lane cannot break its own fence: the renderer recomputes the longest backtick run from the actual fragment bytes at render time rather than trusting the persisted column.

The surviving finding is that the withholding of `propose_covenant` is enforced only at advertisement. The availability flag has exactly two use sites, both in the `tools/list` filter; the handler gates solely on the feature flag, the presence of an ambient capability, and a name match, and never consults it. The verifier found a second, uncited instance of the same gap that strengthens the point: the capability *mint* site ignores the flag too. What the verifier refuted is the consequence. There is no production path that can put the withheld name on the wire — the turn's invocable set is the merged MCP list rather than the handler registry, an unadvertised name is answered with a synthetic "no local tool registered" string and never dispatched, the internal tool cache is per-process and built from a list that a compile-time `false` guarantees never contains the name, the bridge tool binds its name at construction, and both operator-facing direct-invoke routes are closed. So what remains is not an exploitable hole but a real defect of a kind this repository should not tolerate: three security-facing remarks blocks assert a fail-closed handler recheck that no code performs, and the next reader will build on the comment.

Two things were examined deliberately and deliberately not filed, and both are recorded so a later reader does not mistake silence for absence. A scope-bearing lease does satisfy an all-scopes read at the store seam, because the validation returns success early when no scope is required; it is unreachable in production because the only callers are two inspection routes that both acquire an installation-wide read, and every acquisition site of that lease is an operator route or a system maintenance path. And the residence latch moved from key derivation to connection open, so the envelope HKDF root now survives in a process the offline host-tools transition treats as Covenant-free; that transition additionally requires a Development edition, an explicit environment opt-in, the cross-process installation lock, and an inventory that refuses unless the installation holds no Covenant rows or protected artifacts at all — and with no protected state present, a forged token authorises nothing.

## Performance

Examined: the benchmark script, host, workload manifest and all four `Core/Performance` types in full; the per-turn production path from the gate through the admission, the provider-call freeze and the disclosure write; the store query shapes for the turn snapshot, the census, the lane head probe, the list page and the dependent-head scan; and the CI benchmark lane. Two empirical checks were run — the workload manifest digest was recomputed independently in Python and matched byte for byte against a recorded run, and `EXPLAIN QUERY PLAN` was run against a scratch database carrying the real head indexes to confirm the dependent-head scan uses the partial campaign index rather than degrading to a per-campaign scan.

**The per-turn read path is sound and the measurement harness is honest.** No N+1, nothing unbounded, and nothing scaling with installation size where it should be bounded: the turn snapshot is one query, hard-bounded at 160 rows, reading Global plus exactly one Campaign; the census is grouped in SQL with bounded output; the dependent-head scan is one grouped query using the index. Buffers are allocated outside the measured window, the allocation control is measured through the same delegate and the same suspension, negative corrections are reported as failures rather than floored, a null ceiling fails the run instead of reading as unlimited, and the host fails closed on corpus digest, manifest digest, linked-entry counts, empty rendered sections and leaked gate registrations — so a store or linker regression that returned nothing could not make the headline number fast and green.

**The one important finding is the gate's boundary.** The workload declares `turn.plan` to be "the cost the Covenant adds to every live turn... the number an operator feels," and implements it as the snapshot read and link alone. A Covenant-bearing turn also pays, per provider attempt, a whole-transcript envelope freeze with per-content-part digests, and a disclosure write that takes a process-wide semaphore and opens a `BEGIN IMMEDIATE` transaction which the ordering contract requires to complete before the bytes leave. Neither has an operation or a ceiling in the manifest. The heavier of the two is the same class of work as the measured `mutation.commit`, whose ceiling sits an order of magnitude above `turn.plan`'s, so a regression in it passes the gate in silence, and nothing else in the suite bounds it. What makes this actionable rather than a preference is the tree's own disclosure standard: the manifest states the tokenizer substitution explicitly, states the Confirmed-lane-only boundary explicitly, states the Proposed-lane absence explicitly, and the design record volunteers that the per-scope connection open is outside the numbers. Every smaller exclusion is disclosed and the largest one is not.

One minor finding survives: three separate places — the statistics type, the benchmark script header, and the design record — describe the comparative gate as a paired bootstrap over batches co-run and interleaved in one process, which is what cancels machine drift. No co-run mode exists. The host measures one revision and compares against a file another process wrote at another time, and the bootstrap draws one batch index per pair, so batch *i* of each side shares nothing but an ordinal. The statistic is fine for what it is; the documented mechanism is not the implemented one.

Refuted: the claim that runtime-identifier equality being the only host guard is actionable, on the grounds that `osx-arm64` does not distinguish a developer Mac from the shared runner. The mechanics are accurate, but CI never performs a comparison — the only benchmark step gates and records — no baseline is tracked in the repository, and the design record already enumerates the fingerprint fields by name, states that a baseline is comparable only on the host that recorded it, and prescribes recording and comparing on one host. The remaining recommendation is an enhancement, not a correction to a false claim.

Two costs were checked and deliberately not filed. Feature-off is not zero-cost, because the gate reads the session sensitivity projection before any feature check — but that is load-bearing and stated as such in source, since the disclosure obligation survives the feature being turned off. And `mutation.prepare` is genuinely unbounded in the number of Campaigns, because the dependent-head vector it digests grows one entry per Campaign; the manifest admits the growth, and capping the vector would break the binding it exists to produce.

## Repository integration

Examined: the whole CI workflow including step ordering and the artifact pairing, all five locally reproducible checker scripts, the solution and the out-of-solution benchmark host, the machine-readable inventories and frozen contracts, the JSON source-generation registrations for the changed wire shapes, `.gitignore`, and the twenty-five commits read as a sequence for accidental reverts.

**The tree integrates cleanly.** Every CI checker reproducible on this host passes: the blank-line aligner reports zero files needing change, `shellcheck` over `scripts/` is silent, and the coverage-threshold, macOS packaging and AOT-warning self-tests all pass. Every project in the solution plus the out-of-solution benchmark host builds at zero warnings with `--no-incremental`, which matters because incremental builds hide analyzer diagnostics. The benchmark gate was run end to end and exited zero with all five operations inside their ceilings. Ninety-eight inventory and frozen-contract tests pass, and the changed status wire shape and its new enum are already covered by existing serialization registrations, reaching the CLI transitively through the registered parent contract. There are no tracked phantom duplicate files and no conflict markers. The commit sequence is coherent: the two-step withdrawal of the streaming tool-call buffer is one deliberate act completed across two commits rather than a revert, the two tool-withholding commits are complementary rather than contradictory, and the reconciliation commit genuinely reconciles rather than clobbers.

One minor finding survives, narrowed. The CI gate step hard-codes its record filename into the checkout root, and that literal is pinned by the workflow structure test, so a developer reproducing the gate locally — the natural thing to do on a qualification branch — writes that exact file into the working tree, and `.gitignore` has no entry for it. The repository already ignores fixed-name runtime outputs by name, so this is a gap in existing practice rather than a new convention. It stays minor because nothing enforces a clean tree anywhere in CI, no test asserts the ignore file's contents, and runners are ephemeral.

Refuted, and the refutation is worth recording because it turns on provenance rather than on code. The finder cited an untracked recorded baseline sitting beside the benchmark host as proof that the gap was "already present in the tree," and proposed a matching ignore glob. That file is not an attribute of the candidate tree: the name appears nowhere in the repository, no default produces it, and the verifier traced it to a command the orchestrating session itself ran nineteen minutes before the report was written, on a branch whose newest commit is from the previous day. The verifier also established that this was not a read-only violation by the reviewer — the reviewer's own recorded run went to its session scratchpad and is a different file of a different size. The glob is refused; only the CI record filename belongs in the ignore file.

## What these reviews did not cover

**No Windows RID evidence.** The native source manifest reports both Windows runtime identifiers as pending, so the Windows suite lane skips by its own condition exactly as designed. Nothing in this pass exercised a Windows build, a Windows test run, or Windows packaging.

**No execution on a shared CI runner.** Every measurement, build and test run reported here was performed on one Apple-silicon developer host. The benchmark gate's absolute ceilings were exercised locally and passed; whether they hold against the shared runner's distribution is precisely the question the recorded artifact exists to answer, and the finding about that artifact's upload condition is open.

Four further gaps, stated so that "every checker is green on this tree" is not mistaken for "CI passes." The full test suite was not run, by instruction — targeted filters were used instead, each verified to match a non-zero number of tests so that no filter could pass vacuously. The coverage threshold script was not reproduced, because it consumes the output of that full run. The real AOT warning-verification publish was not run; only its self-test was, though the benchmark host's successful Native AOT publish is separate evidence that the compiler and linker work on this host. And each verifier was assigned its own finder's findings, so no verifier re-audited another domain's clean areas — the clean claims in each section rest on one finder's evidence plus, where the consolidation pass re-derived them, a third check.

## Two notes for the maintainer that are not findings

**Clear the build output before any local qualification run.** Running a targeted Covenant filter against the repository's existing release output reds 175 of 2,276 tests, and the tree is innocent. The test project's output directory carries stale package-supplied native SQLCipher libraries under runtime-identifier subdirectories alongside the hermetic asset at the output root; the runtime-identifier copy wins at load time, so the process loads the wrong engine version and the search accelerator tier fails to install against it. The same directory holds phantom duplicate assemblies. All of it is under ignored paths and none of it is tracked. This was proved by extracting the base commit and HEAD into two pristine directories and building each from scratch: on the clean HEAD copy the identical filter is 2,276 passed and zero failed.

**Decide deliberately about the stray baseline file.** The untracked recorded baseline beside the benchmark host was created by this review workflow's own orchestrating session, with a command description suggesting it was meant to be committed — while the benchmark script's header and the README both state that a recorded baseline is comparable only on the host that recorded it, and that comparing a developer machine's baseline against a shared runner would report the runner as a code regression. Whether it is committed or deleted is a decision, not a defect in the candidate tree. It was left untouched.

## Verdict

**ACTIONABLE FINDINGS REMAIN — do not ship this range as qualified until findings 1 through 6 are closed.**

Nothing here is a runtime blocker, and that is not the bar a release qualification sets. Six important findings survive adversarial verification, and they cluster on exactly the surfaces a qualification pass exists to protect: the operator-facing contract of a command surface that became reachable for the first time inside this range and currently instructs an operator to type a flag that does not parse; an inspection surface that reports an admission the turn it claims to describe would not make; a degradation channel that blames an operator's stored data for the linker's own defects; the feature's entire success path asserted by no test, in the file created specifically to assert it; and a release gate whose headline number excludes the heaviest work every Covenant-bearing turn performs, in a manifest that discloses every smaller exclusion. The five minor findings are all one-line or one-paragraph corrections, and four of the five are places where the code and its own documentation disagree — which is the failure mode this range has already demonstrated it can carry through an edit.

The engineering underneath is sound, and the verification pass says so as clearly as it says the rest: no instance of the optional-parameter defect class that killed the two previous audits survives in this range, the shared section arithmetic genuinely removes the duplication it was created for, the security posture holds on every path traced, the store query shapes carry no unbounded or per-row work, and the tree builds and integrates at zero warnings.
