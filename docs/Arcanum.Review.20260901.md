# Arcanum — Whole-Tree Review and Hardening Pass, 2026-09-01

**Date:** 2026-09-01 · **Branch:** `grimoire-fixes`, reviewed at `a1160e88` (45 commits ahead of `main`, 44 files, +27,732 / −110) and re-checked at `c3705d4d` (82 ahead) after the branch moved during the review · **Status:** review complete, remediation plan awaiting approval

Scope: the entire tree — `Core`, `Secrets`, `Infrastructure`, `Api`, `Api.DevHost`, `Cli`, `Compendium.Ux`, `TheForge.Core`, `TheForge.Ux`, the five test projects, and the build, CI, packaging and native-asset surface — with the `grimoire-fixes` delta reviewed at the greatest depth. That delta is the newest and least-reviewed code in the repository: about 18,200 production lines and 9,500 test lines delivering the authenticated offline-transition journal, the typed transition lifecycle, and the process-local Grimoire admission gate. Four domains were reviewed for every slice: reliability, security, performance, and usability, with test honesty and documentation truthfulness treated as first-class categories because this repository's own history says they are where its defects hide.

This pass inherits the standard of evidence the 2026-08-25 pass established after five consecutive audits each found the same defect class — a passing test standing over broken production behaviour because the test reached the code a way production never does. Every finder was therefore required to name the production call path under `src/` with `file:line` for anything claimed reachable, to re-derive every line number by search rather than memory, and to tag any observation about the not-yet-activated admission and transition types as unwired-by-design unless a governed document claimed otherwise. Two facts fixed the frame for those types: the gate's *opening* side is live on every production connection, because the enrolment interceptor is installed on both serving `DbContext` compositions, while its *closing* side has no production caller by approved plan.

## Method

Twenty-two read-only finder agents ran in one wave, each assigned a bounded slice and the same brief: six on the branch delta (the gate, the EF wiring, the journal file primitives, the journal crypto and store, the lifecycle and shared security changes, and an end-to-end acceptance-coverage audit of the delta's tests), fourteen on the rest of the tree by subsystem, one cross-cutting sweep of twenty-four defect signatures over every production file, and one backlog re-triage that re-derived the eleven findings the 2026-08-25 pass carried into remediation. Finders were structurally read-only — the `Explore` agent type has no edit tools — because on an earlier pass review agents silently reverted three guards in the files they were reviewing.

Every non-clean finding was then handed to an **independent adversarial verifier** for its slice, whose default verdict was *refuted*, which re-opened every cited file, re-derived every line number with `grep`, traced the production path itself, and for test-honesty findings performed the described mutation against the actual test code before deciding whether it would stay green. Verifiers also re-rated severity independently: blocking for data loss, a security breach, or a documented guarantee that is false in production today; important for a defect a maintainer must fix before relying on the component, or a test that proves nothing about an acceptance claim; minor for real but bounded or latent.

The verification pass mattered in both directions. 39 findings were refuted outright, several because the verifier found the guard the finder missed or ran a mutation the finder had only described and found it caught. 110 survived only in narrowed form. And in 66 cases the verifier found the defect wider than reported — including one blocking defect no finder had filed at all, found while chasing a neighbouring finding, and two more found by the agents that re-checked the tree after the branch moved: the labelled-artifact guard on the Grimoire repository is an optional constructor parameter that no production registration supplies, so a documented refusal is dead code. One low-confidence finding about a variadic system call was settled by disassembling this machine's own kernel library rather than left as a hypothesis.

## The branch delta: admission gate, transition journal, lifecycle

Examined line by line: `GrimoireConnectionAdmissionGate.cs` (2,636 lines) and its contracts; `CovenantConnectionEnrolmentInterceptor.cs`, `ArcanumDbContext.cs`, `ArcanumDbContextOptionsConfigurator.cs` and the DbContext registrations in `ServiceCollectionExtensions.cs`; the journal file primitives and file store (4,286 lines); the journal store, authenticator, key provider and anchor store (3,365 lines); the lifecycle validator, store, registry and JSON contexts; the shared backup-journal authenticator and key provider the branch generalised; and every test file the branch added, read against the acceptance criteria of the three delivered children.

**The engineering is largely sound, and the verifiers said so in specific terms.** Every `TaskCompletionSource` in the gate is created with `RunContinuationsAsynchronously`, so the several completions signalled under the lock cannot run a consumer inline. The external-effect frontier is genuinely atomic: the revocation set is computed under the same lock that `TryBeginExternalEffectGroup` takes, and cancellations are issued only after the lock is released. The AES-256-GCM tag is verified before any plaintext-derived decision on all six decode paths, the JSON surface is fully source-generated with size caps applied before parsing, and the associated-data binding is the strongest test in the delta: all nine header fields are mutated through the outermost production `Seal` and `Open`, and the byte layout is pinned independently against a hand-recomputed frame. No test in the gate suite contains a `Task.Delay`, a `Thread.Sleep` or a spin; every race is driven by manual time and barriers. The lifecycle edge table is closed, no arm lets a retired or parked slot resume without proof, and every same-state arm requires strict progress so no advance can burn a journal revision on an identical payload. The extraction of the stable key lease did not regress the backup restore-journal path, and no credential was dropped from the installation-reset delete set.

**What is wrong is concentrated in three places: cancellation, the anti-rollback anchor, and the Windows arm.**

The repository's own recurring root cause — compensating work refused on the token that just failed — appears four times in the new code. `CloseConnectionAdmissionAsync` commits the whole stage-two transition inside its lock (generation bump, state `Closed`, refusal stamped on every unresolved open) and only then checks the caller's token at `GrimoireConnectionAdmissionGate.cs:529`, so a call with a pre-cancelled token closes admission while reporting cancellation, burns a generation, and closes the in-flight opens under their users. `ClosedLease.CompleteAsync` throws on a cancelled token at `:2603` before reaching `CompleteClosedLease`, which is the only transition from `Closed` back to `Ordinary`; the verifier narrowed the consequence — a same-owner retry can recover — but noted that the obvious cleanup reflex, disposing the lease, clears the active lease without touching the state, so an `await using` unwind leaves the gate closed with no diagnostic. `AbortClosingAsync` refuses on a cancelled token and forwards it to the safety proof at `:609`–`:611`, though here the check precedes any mutation, so the cost is one extra drain round-trip rather than a wedge. And in the journal file store, every statement after `published = true` at `GrimoireOfflineTransitionJournalFileStore.cs:629` — the landed inspection, the reread, predecessor retirement, the residue proof — runs on the caller's token, so a cancellation that lands after the rename has irrevocably succeeded converts a correct publication into `Data.RecoveryRequired` and strands the `.previous` file; the verifier found the first-publication branch at `:659` has the same window. The sibling `DeleteDurably` and `ProveAbsentDurably` already pass `CancellationToken.None`, which is the house pattern.

A leaked maintenance handle wedges the process. Once the gate is `Closed`, `CompleteClosedLease` refuses while any tracked maintenance handle is live, `AbortClosingAsync` refuses because the state is not `Closing`, and disposing the lane blocks forever on `await lane.HandlesDrained` at `:1704` with no timeout while still holding the process-wide adoption semaphore. The verifier's addition matters for the fix: `IGrimoireTrackedMaintenanceHandle` is the only capability in the contract file with no `Dispose` or `DisposeAsync`, so a caller cannot write a `using` guard against the leak even if it wanted to.

The anti-rollback anchor fails open when it is missing. `BeginAsync` at `GrimoireOfflineTransitionJournalStore.cs:282` treats an absent anchor as never-provisioned whenever all journal files are also absent, calls `CreateOrOpen` — which silently returns a pre-existing key — and writes a fresh closed genesis at slot epoch zero; `RecoverAsync` at `:825` mirrors it by returning `NoActiveJournal`, which the design says permits readiness. The design does not sanction this: it removes key and anchor together only during a full installation reset, and says the first operation compares from the exact *provisioned* genesis. The verifier went further than the finder and named the admitting site: `AuthenticateOneAhead` at `:1451`–`:1477` accepts a file whose predecessor digest is the zero digest when the anchor is at revision zero, matching only the profile, installation, slot epoch, operation, kind, version and location — every one of which recurs after the epoch reset when the same database-derived operation is retried — so a retained pre-deletion envelope authenticates under the same key in the reopened window. `GrimoireOfflineTransitionJournalKeyProvider.IsPresent` exists for exactly this check and has no caller anywhere. The test named `Recover_returns_no_active_only_for_proven_anchor_and_file_absence` asserts only the both-absent positive case; the arm that fails open has no test, and the design's regression catalogue credits this suite with refusing rollback.

Two smaller journal findings share a shape: a transient credential-store outage while reading the key collapses to `ManualRecoveryRequired` at `:849`, `:1146` and `:1389` — the terminal disposition whose documented remedy is a destructive reset — while an identity failure four lines earlier propagates its own code; and an anchor *read* failure, including the integrity failure the anchor store raises on a non-canonical or mis-bound anchor, is folded into `RevisionConflict` at `:602`–`:606`, inviting a retry loop against tamper evidence.

The lifecycle validator cannot park twice. Once a `KeepClosed` blocker has been resolved, the payload carries resolution evidence, and the edge back into `KeepClosed` requires that evidence to be null; the preservation rule at `GrimoireOfflineTransitionLifecycleValidator.cs:43` cannot be satisfied either way, so a second failure has no legal exit and the slot stays active forever. The verifier confirmed the same defect in the healthy-catalog handler at `:88`–`:97`. Related and plausible rather than confirmed: the resolution proof compares both fields of the two-field evidence record to the one digest already stored in the current payload, so the state-digest field is dead and a producer that computes a genuine state digest would be refused; no producer exists yet, which is why it is plausible.

The Windows arm is written but unproven, and one part is wrong on the shipping macOS target. The atomic exchange is the one mutation performed by absolute path through `ReplaceFileW` rather than relative to the retained no-follow parent handle, at `GrimoireOfflineTransitionJournalFilePrimitives.cs:594`–`:597`; the verifier narrowed the exposure, since the next step re-inspects through the parent handle and the identity comparison catches a redirected write, but the anchoring invariant every other mutation honours is broken here and it is the only mutation that omits the trailing parent validation. Separately, a low-confidence finding about the variadic `openat` declaration at `:1864` was settled by disassembling this machine's kernel library: on Darwin arm64 `openat` reads the creation mode from the caller's stack, never from the fourth register, so the fixed-arity P/Invoke delivers an arbitrary word as the creation mode and only the later `fchmod` establishes 0600. Exposure is blocked by the mandatory 0700 parent posture, but the mode passed is undefined and can include set-id bits that the umask does not strip. The repository's other `openat` declaration always passes mode zero without `O_CREAT`, so it is unaffected.

`ResumeWorkingPublicationAsync`, the entry point for the promised one-revision-ahead recovery, has no exception handling at all, so the same conditions its sibling converts to a `Result` — including the caller's cancellation and both of its own injected crash seams — escape as thrown exceptions; `NormalizeWorkingPredecessorAsync`'s only catch filters on an exception no code in its call tree can throw. And whether NTFS reports a zero link count on a handle whose file has a pending POSIX-semantics delete could not be settled read-only; if it does not, every retirement and delete on Windows returns recovery-required, and no test executes that branch on any platform.

**Test honesty in the delta.** The acceptance-coverage audit mapped twenty-seven claims across the three delivered children: twenty-three covered, two partial, two with no test — and after verification the two uncovered ones were judged out of the delivered child's scope, so they are recorded here rather than counted. What survives is narrower and more concrete. The inventory test meant to fence every DbContext-options path matches nothing in production: its literal `ArcanumDbContextOptionsConfigurator.Configure(optionsBuilder` selects zero files because both real call sites break the line and name the argument `options`, and its other literal selects only the one file the test exempts; two of its three named exemptions are dead, and it was dead at the commit that introduced it. Five tests in the journal file store suite assert on the production file's *source text* — `File.ReadAllText` plus `Assert.Contains` — rather than on behaviour, the strongest of which passes only because the call it forbids is spelled as a method group without a following parenthesis; replacing `ApplyWindowsOwnerOnly` with `return true` leaves all five green. The durability promise is asserted only through the store's own unconditional step-name emissions, so removing every `fsync` from the implementation changes no assertion, and on Windows the directory flush is a hard-coded `true`. The refusal path's "physically closed" claim is asserted against `:memory:` with pooling off using a state-change counter, and the interceptor's own exception message repeats the overclaim while the only check behind it is `ConnectionState.Closed`; two verifiers split on the consequence, and both agreed the branch is unreachable until the closing side is wired. The test named for caller-asserted blocker resolution *does* catch the mutation the finder described — that one was refuted — as were four other test-honesty candidates in the lifecycle suite, each because the verifier found the assertion the finder had missed.

Refuted in this domain, with the reasons recorded so silence is not mistaken for absence: the claim that a promoted request's context can open a foreign connection through a nested work lease describes the approved design, pinned by the plan's own GREEN code; the sticky stage-one timeout flag lets an owner abort after a successful re-drain, which the suite deliberately keeps open; the anchor compare-write is protected by the exclusive file lock whose liveness `AssertHeldFor` enforces, not merely asserted; the closed handler registry cannot fail to compose for the two fixed handlers and a test touches `Production` on every run; a lifecycle payload with a null `Lifecycle` requires a null-forgiving cast under enabled nullability; the shared AAD length literal *is* pinned, because `Seal` returns invalid if it drifts and the byte-layout test decrypts under the rebuilt frame; and the "only" in the pooled-handle claim fell to the drain test that sets pooling on, asserts the sidecar survives disposal, and asserts it is gone after the drain clears the pools.

## Reliability across the tree

Examined: the retention service and its pruning partial (14,688 lines) and the Covenant data layer; the schema catalog, evolution planner, busy-retry helper, operation store and the raw SQLite openers; the backup archive codec, restore service, session importer and Covenant restore coordinator; the long-running-operation reconciler, recovery registry, daemon runner and installation-reset probe and cleanup; the hosted services, provider health probe, Saga extraction, logging sink and metrics exporter; and a grep-driven sweep of twenty-four defect signatures over every production file.

The fourth blocking defect is in backup restore. No test passes more than one Session to this path.

The Saga extraction consumer awaits its retry backoff inline in a single-reader loop, and releases its dedupe key at dequeue rather than completion, so one failing session stalls the queue and a turn that finishes mid-extraction pays a second model call; the verifier corrected the backoff arithmetic to a fifteen-second ladder rather than five minutes. The rolling file sink sets no size limit, so one pathological day silently drops every event past Serilog's one-gibibyte default. `workspace_check` spawns `sandbox-exec` synchronously on every invocation and, the verifier found, on every tools-list as well. ## Security across the tree

Examined: the host-process-tools runtime policy and startup gate, `SanctumGuard`, the credential stores on all three platforms, the outbound URL guard, the HTTPS certificate loader, the ward gate, the marker store, the file-encryption key provider, the API-key digest cache, the idempotency filters, the Covenant endpoint conventions, the workspace path policy and every file tool, the process runners, and every interpolated string near SQL.

**One blocking defect, and it is a documented guarantee that is false.** The startup gate publishes a runtime decision carrying `HostProcessToolsPermitted`, and exactly one site under `src/` reads it — the bootstrapper, which merely copies it into the blocked decision. Every advertise and invoke site instead calls the legacy edition-plus-environment predicate, which reads the same two inputs the probe reads. So on a Development host started with the escape-hatch variable but no completed taint transition, the gate blocks with `EscapeHatchWithoutTransition`, the bootstrapper deliberately degrades rather than stops, and the tools are advertised and invocable anyway — while the threat model in the design states the host "exits ... rather than advertising the tools". The verifier found the degraded branch writes nothing durable, so the next start without the variable republishes the Covenant as permitted on an installation where model-driven code already ran with the operator's OS identity, which is the evidence loss the two-marker protocol exists to prevent.

`SanctumGuard` fails open when a Campaign disappears mid-turn: the pipeline captures the Campaign once per turn, the guard re-resolves it per call, the repository's delete is a hard `ExecuteDeleteAsync` with an untracked reader, and an id that no longer resolves collapses to a null config that every validator treats as full permission at `SanctumGuard.cs:397` — while a malformed id is denied. The verifier found a second entry with no resolution guard at all, gated only on the id being non-blank, and concluded the fix must cover both. The workspace path policy itself is clean: reserved device names, extended and UNC prefixes, and trailing dot-and-space aliases are all closed, the case-sensitivity asymmetry on macOS can only reject, and the tools missing from the pipeline's path switch are ones that cannot reach a path.

## What was refuted, and why it is recorded

Thirty-nine findings were refuted and are not carried. The reasons cluster into five kinds, and each is worth knowing because the same kind will be reported again: the guard the finder missed was one frame away (a bare catch below a filtered one, a disposal that rolls back, a collection attribute that serialises the tests); the behaviour is the documented and deliberate contract (the page-size drain, the readiness latch, the empty upload allow-list, the benchmark ceiling, the PID-file policy, the Linux re-probe); the failure state is not constructible (a filename longer than the volume allows, a filesystem write inside a sub-microsecond mtime window, a handle race the generic host's stop sequence excludes, a dispose race with the only implementation); the doc sentence is imprecise rather than false and a maintainer would leave it standing; or the mutation the finder described is actually caught by an assertion the finder did not read. The full per-finding verdicts, including every refutation with its decisive line, travel with the plan.
