## Working rules

1. **Branches.** Work on a branch per task (or per phase for the Minor wave) cut from `claude/codebase-review-2026-10`, or from `general-enhancements` if that branch has moved past it; merge each back with `git merge --no-ff`. `main` is not touched until the final delivery step. One plain git command per shell call in this repository's agent tooling; `rg` needs a `RIPGREP_CONFIG_PATH=` prefix.
2. **Test first, every time.** For each finding: write the test that reproduces the register's failure scenario (start from the reviewer's probe when there is one), run it on the unchanged tree and watch it fail for the stated reason, then make the smallest production change that passes it, then re-run the unit's existing test classes. Finish with a mutation check: revert or break the fix and watch the new test fail; restore it. Quote the red failure in the commit message. A test that passes before the fix proves nothing and must be rewritten.
3. **House style and platform rules** are in `AGENTS.md` and `docs/Arcanum.Engineering.md`: one blank line between ordinary member and statement lines but never immediately inside parentheses, brackets or braces; file-scoped namespaces; positional records for DTOs; no `[JsonPropertyName]` on `/api` wire types; primary constructors for DI. Native AOT throughout: no reflection-based `JsonSerializer`, every `/api` payload type registered on `ArcanumJsonContext`, configuration POCOs with `{ get; set; }`. In the Grimoire, EF Core is the compiled-model, change-tracking, `SaveChanges` and transaction lane only; every application read, filter, order, aggregate, page and set-based write is parameterized direct SQLite on the admitted connection. Schema changes are a `.sql` file per object under `Infrastructure/Data/Schema/**`, never a numbered migration. Formatting checks before each commit: `python3 scripts/align_csharp_blanklines.py --repo . --check <changed .cs files>` (also with `--compact-delimiters`) and `dotnet format whitespace --folder --include <changed .cs files> --verify-no-changes`.
4. **Docs travel with code.** Architecture, persistence and testing changes go to `docs/Arcanum.DESIGN.md`; HTTP contract changes to `docs/Arcanum.API.md`; CLI surface changes to `docs/Arcanum.Command.Reference.md`; configuration keys to `docs/Compendium.README.md`; operator narrative to `docs/Arcanum.Design.Human.md`; debugging steps to `docs/Arcanum.DEBUGGING.Human.md`. Update the owning document in the same commit as the code. Governed documents never name a tracker issue (the documentation tests refuse `#NNN`); say what is true instead. The root `README.md` changes only for an intentional public-page change.
5. **Names.** New domain concepts must fit the established vocabulary (`Campaign`, `Spell`, `Ward`, `Sanctum`, `Grimoire`, `Apprentice`, `The Weave`) unless they are universal terms; prefer not to introduce new concepts at all. Use plain names for anything mechanical.
6. **Suggested fixes are suggestions.** The register's fix is the reviewer's; if the code shows it is wrong, incomplete or would break a documented contract, write the better fix and say in the task notes why. Never weaken a guard, a boundary test, a schema constraint or an analysis gate to make something pass.
7. **Record outcomes without rewriting the register.** Append a section `## Remediation record` to the end of the register listing every `RV-` id with one of: `fixed <commit>`, `refuted <evidence>`, `parked <owner ruling>`; parking needs the owner's word, not the executor's.

## Part B — completing the review

Appendix A lists the 76 units; those without ✔, and the lenses still owed on partially reviewed units, remain. For each: read every file of the unit in full (no sampling), then the owning sections of DESIGN, API, Command Reference and Compendium.README, then prove each suspected defect with a probe test, a deliberate break that the existing tests miss, a measurement, or a traced call path when execution is not feasible. Lenses:

- **Reliability:** swallowed or over-broad exception handling; cancellation not propagated or turned into the wrong outcome; disposal and resource leaks (streams, processes, connections, semaphore counts, token sources, event subscriptions); check-then-act races, lock scope, async void, unobserved fire-and-forget; sync-over-async; crash consistency (write-then-rename, transactions, journals, idempotent recovery); retry and idempotency; startup and shutdown ordering; queues without backpressure; data integrity (constraints vs code, nulls, off-by-one on bounds and pages, overflow, clock assumptions); macOS vs Windows differences; Native AOT pitfalls; tests that pass for the wrong reason.
- **Performance:** hot paths (turns and token streaming, tool execution, retrieval and embedding, indexing, SQLite, startup, the TUI loop, backup and restore, Long Rest); N+1 queries and missing indexes against the schema; repeated work (regex compilation, re-serialization, re-reads); allocation on hot paths; blocking I/O and locks held across awaits; unbounded growth (caches, journals, dictionaries keyed by input); quadratic complexity over data that scales; measurements, not adjectives.
- **Usability:** CLI names, help, error text that says what to do next, exit codes against the 0/1/2/3/130 contract, `--json` as one document with diagnostics on stderr, confirmations, `--plain` and `NO_COLOR`, agreement with the Command Reference; API envelope and status consistency, error bodies naming the field, documented limits, agreement with `docs/Arcanum.API.md`; TUI, Compendium and Forge responsiveness, feedback, focus, state kept on error, colour-only signals; configuration keys, defaults and validation messages against `docs/Compendium.README.md`; model-facing tool descriptions, schemas and error text; diagnostics an operator can act on; documentation that disagrees with the code.

A finding needs a file and line, a concrete failure scenario or measured cost, evidence, a suggested fix and an effort (S under an hour, M a day, L more); never style, naming or design preference. Then have an independent second reader try to refute each finding (does the scenario happen; is it already handled, tested, deliberate per the docs, or ruled by the owner) before adding it to the register and this plan. Continue the `RV-` numbering. A strong model for reliability and a cheaper one for the other two lenses was the owner's preference.
