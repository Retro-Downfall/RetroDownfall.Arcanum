# RV229: usable partial blob inventory without false completion

The native metadata store currently aborts enumeration on a malformed identity or escaped attachment path. Status/migrate/verify/key rotation all call it first. The lifecycle also completes an ordinary durable operation even when its own returned result contains failures, and sums attempt plus verification failures so one bad file can be reported twice. These adjacent behaviors must be tested and repaired with the inventory change.

Proposed contract: return an explicit BlobEncryptionInventory with separate valid Candidates and InvalidRows, not an invalid candidate with an empty path. Each invalid row carries its closed record kind, native catalog rowid, closed failure category and known nonnegative size when readable. No arbitrary Id/path/exception text enters logs. Preserve raw valid stored GUID spelling for write-back. Listing continues for healthy neighbors; native database errors and cancellation still propagate. Add a required typed logger to the native store. A vanished write-back row should yield a per-row InvalidDataException naming only a safe locator, allowing other candidates to continue.

Status counts invalid metadata in InvalidFiles and totals; each byte total is nullable: an unreadable contributing size or a sum beyond Int64 makes that total unknown, while exact file counts remain available. The CLI prints `unknown` for these totals. Remaining bytes are summed from the current failed rows directly, never calculated by subtracting overflowing totals. Verification returns InvalidMetadata issues while processing every valid candidate; no file I/O is possible for InvalidRows. Normal migration/rotation and recovery process healthy candidates but retain a non-success durable state and exit result when any invalid row remains. Track failed record identities across attempt and verification so one record is counted once; preserve a vanished record's attempt failure even when the final inventory no longer contains it.

Key retirement must refuse an incomplete metadata inventory. Re-list immediately before retirement, and if a new invalid row appears after verification, preserve all old keys, return a failure result and retain reconciliation-required state. Move completion after this last rotation precondition; cancellation remains distinct from invalid inventory. Do not add schema changes or automatic repair/deletion of malformed rows.

TDD: native corrupted row beside healthy uploaded and attachment records, exact row locator with private canaries excluded; status/verify/migrate/rotation healthy-neighbor progress; failed counts not doubled and durable state not Completed; invalid metadata arriving only at final retirement; recovery mirrors those semantics; row deleted before write-back; native busy/cancellation preserved. Keep healthy spelling, missing-file, key/cancellation controls. All isolated files/keyring/SQLCipher fixtures, no installation or live provider use.

## Independent design review incorporated

The read-only review at `/private/tmp/arcanum-blob-metadata-recovery-plan-review.md` confirms the direction and identifies the exact lifecycle boundaries. Carry signed `(kind,rowid)` on valid and invalid native rows; it is a per-pass diagnostic identity, never a rowid-only mutation capability. Validate raw SQLite storage types before narrowing and preserve legitimate free-form uploaded purposes. Do not coerce REAL/TEXT lookalikes to integers or accept negative/overflowed lengths. Aggregate byte arithmetic must be checked, with unknown-size reporting rather than a fabricated exact total.

Merge attempt/final outcomes by record identity, preserving a vanished attempt failure and distinct failures in both passes; never use `Issues.None` for a failed write-back. One operation owner settles only after verification and key-retirement preconditions. Check every settlement compare-exchange result and report an operation-level finalization failure without inventing a file failure. Handle acquisition-to-finalization failures, including initial inventory and initial key rotation, under that same ownership boundary. Keep existing per-file replacement cancellation semantics and do not overwrite an adopted operation.

A final incomplete inventory retires no key. Distinguish it from cancellation; individual key retirements persist separately, so a later persistence failure never implies rollback of prior successful retirements. The CLI already holds the exclusive installation lock for the whole command. A metadata re-list and key-store writes are not a cross-resource atomic transaction against arbitrary external SQL; no stronger lock promise is introduced here.

TDD order: native corruption/healthy-neighbor and locator/privacy/type cases; per-record attempt/final counting; durable outcomes; final-inventory retirement refusal; settlement, key persistence and cancellation; recovery counterparts. ## Implementation findings and evidence boundary

Native tests exposed silently coerced REAL/TEXT numeric cells and BLOB-valued string fields, in addition to bad identities and escaped paths. The initial native cycle produced12 genuine failures and2 healthy controls, then14 passes. The next lifecycle cycle produced15 genuine failures, then25 passes with existing controls. Six further recovery/ownership/large-physical-I/O failures were reproduced, then the combined native/lifecycle classes passed45 tests. These are incremental gates, not final qualification.

A valid catalog size cannot be trusted as a throttle reservation: a wrong Int64-sized value overflowed scheduling before any healthy neighbor could proceed. Reserve from actual file length, in bounded scheduling steps, and preserve cancellation even for large physical files. Recheck durable ownership after waiting and before starting another atomic blob transition. Preserve an initial invalid-row refusal throughout that invocation even if an external change removes it before the final scan.

Verification also must compare catalog encryption version/key to the authenticated envelope, while migration remains able to repair stale metadata. Initial acquisition, key creation, verification and retirement all belong inside the owned attempt. If settlement itself fails, preserve both the primary and settlement failures; cancellation remains an OperationCanceledException. A lost lease never permits a zero-failure success or overwriting the new owner. No exception messages or raw catalog content enter durable error codes.

## 2026-10-27 independent review: expired lease repair

The provisional review confirmed that owner/state checks alone admit an expired lease. The real native store refuses heartbeat renewal after expiry, but fake heartbeats always succeed. Add native behavioral REDs expiring the exact owned row after initial, verification and retirement inventory reads in both foreground and recovery. Prove no next mutation/retirement or successful completion. Then require a live owned lease and renew at phase boundaries and bounded throttle waits without background tasks. Preserve atomic in-flight blob transitions and owner/revision CAS for failure settlement; expired still-owned work may be marked incomplete without reacquiring mutation authority. Make recovery fixtures hold legitimate unexpired leases, retain cancellation/ownership/settlement controls, run complete affected classes/build/styles, and return an uncommitted repair diff for root review.

The expiry repair first produced10 genuine native RED failures on unchanged provisional production, then passed all10. New renewal checks exposed invalid old recovery fixtures (null/expired leases or null coordinators); those were corrected to actual live ownership, retaining the original assertions. A focused settlement fixture now injects its secondary fault only after the primary failure, so a new earlier lease read does not replace its intended trigger. A missing test import caused one disclosed compile-only abort, excluded from behavioral RED.

Six additional native RED cases proved that cancellation during any inventory phase must retain just-observed invalid metadata, in foreground and recovery. Failure recording now precedes renewal/cancellation checks and recovery shares its per-record failure knowledge through verification and retirement. A separate post-heartbeat cancellation race produced1 RED with7 positive renewal/refusal controls; cancellation after renewal now keeps its public cancellation shape. Positive native controls advance logical time beyond the original lease while proving real native renewals; they do not wait15 wall-clock minutes. No schema or shared operation-store authority change is required.
